# 流水线为什么要并发

## 1. 业务步骤与执行方式是两回事

业务仍然是：

```text
读取视频 → 推理 → 跟踪 → 规则 → 告警保存
```

进程、线程、队列决定这些步骤由谁执行、是否等待、数据在哪里交换。把一段函数拆进新进程，不会自动增加显卡计算能力。

最简单的单线程循环可以逐帧完成全部步骤；对于离线文件、不要求实时、单路吞吐足够的任务，这是一种可行实现。是否增加并发，应从等待点和目标吞吐判断。

## 2. 单线程为什么可能跟不上

假设一帧各阶段耗时：

| 阶段 | 假设耗时 |
|---|---:|
| 等待并读取画面 | 15 ms |
| 推理与跟踪 | 35 ms |
| 规则 | 1 ms |
| 图片保存 | 20 ms |
| 合计 | 71 ms |

如果所有步骤严格串行，处理能力约为 1000/71≈14.1 帧/秒。若网络请求偶尔等待几秒，整个循环也会跟着等待。

多路再逐路串行时，某一路读流长时间未返回，会推迟后续各路的处理。这是引入独立读流执行者的重要理由。

这些数字只演示串行等待的计算方法，不能用于估算本项目实际容量。

## 3. 流水线并发改变了什么

让读取、计算、保存分别推进时，读下一帧可以与处理上一帧重叠：

```mermaid
flowchart LR
    R["读取执行者<br/>持续读各路"] --> Q1["输入缓冲"]
    Q1 --> I["推理执行者<br/>计算与跟踪"]
    I --> Q2["结果或事件缓冲"]
    Q2 --> O["保存执行者<br/>编码、写盘、请求"]
```

在理想的独立阶段、资源充足且忽略通信成本时，流水线吞吐受最慢阶段限制，而不是各阶段耗时相加。按前面的假设，最慢阶段 35 ms 对应约 28.6 次/秒的上界示意；实际还要考虑共享 CPU/GPU、数据复制、批量、丢帧和排队。

一帧仍必须经历自己的处理步骤，所以吞吐改善不等于单帧延迟自动变成 35 ms。排队还可能增加端到端延迟。

## 4. 本项目具体拆了什么

| 执行者 | 当前职责 | 拆分用途与边界 |
|---|---|---|
| HTTP 服务进程 | 目录、选流、状态、启停 | 与检测生命周期分开，检测计算在另一进程 |
| stream_batch 子进程 | 组织 reader、SHM、状态通知 | 管理多路输入；额外管理层也是框架选择 |
| 6 个 reader 进程 | 每个管理两路 | 当前十二路 6×2 分组，不是唯一可能拓扑 |
| 每路读帧线程 | 管道读取、连接与重连 | 一路等待不直接占住同组另一条读帧线程 |
| 每路 FFmpeg 子进程 | 媒体拉流、解码、滤镜 | 使用外部程序处理媒体，并经 stdout 输出 |
| infer 子进程 | 批量模型推理、逐路跟踪 | 集中管理模型与 CUDA 相关资源 |
| rule 子进程 | 业务窗口、轨迹计时、事件 | 复用公共子管道框架；不意味着规则必须独占进程 |
| preview_save/upload 线程 | 图片处理、落盘、按模式请求 | 让 I/O 与计算分别推进；队列满时仍可反压主管道 |

当前十二路在一个 infer 子管道中批量推理，不是十二个独立模型进程。跟踪也在 infer 内执行，没有专用跟踪进程。

## 5. 为什么同时用线程和进程

线程共享同一进程的内存，创建与对象交换通常较轻，适合组织 I/O 等待；共享状态也需要锁、队列或明确的访问约定。常规 CPython 3.10 的 GIL 会限制同进程 Python 字节码的并行执行，原生库和 I/O 的行为要分别看。

进程拥有独立地址空间，可分开执行 Python 工作、管理资源和生命周期；代价是启动、内存、序列化和进程通信。程序还需要监督退出和回收资源。

这些基础语义参见 [threading](https://docs.python.org/zh-cn/3.10/library/threading.html) 和 [multiprocessing](https://docs.python.org/zh-cn/3.10/library/multiprocessing.html)。多进程不等于完整故障隔离：父进程仍需要监督子进程，外部程序和共享资源也需要清理。

本项目 runner 尝试使用 spawn，注释说明为避免继承不可直接复用的 CUDA context。依据：`core/pipeline/runner.py:47`，`run_pipeline()`。若启动方式已经设置，代码捕获 RuntimeError 后继续。

## 6. 为什么还有 stderr、退出监听等辅助线程

每路 FFmpeg 除了画面输出，还可能持续输出错误信息。本项目用专门线程读取 stderr，读帧线程处理 stdout。reader 中另有退出监听与协调线程，把进程级停止信号传到各路工作循环。

这些线程不执行新模型，而是处理不同阻塞点、状态和生命周期。

依据：`core/stream/backends/ffmpeg.py:247/273`，`_drain_stderr()/_start_proc()`；`core/stream/ffmpeg_reader.py:80`，`ffmpeg_stream_process_entry()`。外部程序与管道语义可读 [subprocess：Popen、PIPE 与 communicate](https://docs.python.org/zh-cn/3.10/library/subprocess.html)。

## 7. 共享内存和队列是并发设计的配套

普通 multiprocessing.Queue 消息需要序列化。大图像若在多阶段反复入队，会带来复制与序列化成本；本项目把 live 像素放到共享内存，队列传名称、shape、序号等通知。

infer 再复制到 snapshot，检测结果经队列送给规则；告警线程任务可以携带主管道已经拷贝的截图。不能泛称所有队列都只传元数据，也不能把这条链称为端到端零拷贝。

依据：`core/pipeline/session.py:70/123`，`_make_queue_pair()/create_pair()`；`core/ipc/frame_batch_shm.py:219`，`copy_from()`；`project/camera_sys/core/pipeline/main_pipeline.py:139`，`_forward_upload()`。

学习资源：[SharedMemory](https://docs.python.org/zh-cn/3.10/library/multiprocessing.shared_memory.html)、[queue](https://docs.python.org/zh-cn/3.10/library/queue.html)。

## 8. 并发并没有消除瓶颈

| 消费慢的阶段 | 当前策略可能产生的效果 |
|---|---|
| infer | 容量 1 的任务队列丢旧通知；未必检测每一帧 |
| preview_save | 丢旧任务，优先较新的结果 |
| rule 输出、upload 输入 | 不主动丢旧消息；满后阻塞 |
| 磁盘或网络持续很慢 | 积压和阻塞可能沿主管道向上游传递 |

依据：`project/camera_sys/configs/pipeline.yaml` 中各 session；`core/pipeline/session.py:177`，`_put()`。

假设生产 30 项/秒、消费 20 项/秒且一直维持，等待量净增约 10 项/秒。把队列从 10 扩到 100，只会推迟满队列的时间，不会把消费者提高到 30 项/秒。实时系统通常还要明确选择“处理全部历史”还是“优先新画面”。

## 9. 所有拆分都必要吗

从功能上，读取、推理、规则和保存可以在一个程序循环完成。当前设计同时服务于多路实时输入、资源管理、HTTP 控制和公共框架复用。

特别是简单规则单独一个进程、stream_batch 管理层、reader 的 6×2 分组，属于有取舍的实现选择。规则并不因为独立运行就必然更快。更少执行者可能减少 IPC 和清理复杂度，但必须保持读流、帧身份、规则顺序和慢 I/O 等边界。

这只是架构判断，不是修改建议或已验证的替代方案。调整前应先测量每阶段耗时、不同帧处理率、队列等待、端到端延迟和故障退出。

## 10. 怎样验证拆分是否值得

1. 固定视频、路数、模型、输出频率和后台负载。
2. 分开记录读取等待、CPU 预后处理、GPU 计算、规则和图片写盘时间。
3. 区分不同帧处理率与重复计算次数，记录队列积压、丢弃和延迟。
4. 单独拖慢一个视频源或本地测试输出，观察是否影响其他源。
5. 只在隔离副本比较某一项拆分，避免同时改拓扑、分辨率和模型后无法归因。

CPU 可用 perf_counter 和线程栈；GPU 异步计算应采用合适的 CUDA 计时方式，不能把 Python 调用返回时间直接当成 GPU 完成时间。

## 12. 自测与练习

- 一路摄像头断流时，哪些执行者会等待，哪些应能继续推进？
- 为什么把告警放进线程后，队列满了仍可能影响主管道？
- 同一张 GPU 上启动更多模型进程，可能增加什么开销？
- 为什么整机 CPU 利用率、GPU 计算利用率和解码引擎利用率要分开观察？
- 怎样证明某次吞吐提升来自并发，而不是降低了处理帧率？

迁移练习：在独立小脚本中，用 sleep 模拟读取与保存，用一个有限队列连接生产者和消费者；比较串行、阻塞队列和丢旧策略。sleep 模拟的是等待，不能用这个练习证明 Python CPU 密集代码绕过了 GIL。
